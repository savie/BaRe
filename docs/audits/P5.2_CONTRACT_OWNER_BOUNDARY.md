7. dependencies

Owner rule:
- one canonical owner per contract;
- Activity/Fragment remains a consumer when a domain/service/repository boundary is evidenced;
- provider/backend execution remains behind the appropriate contract when outside the current authorization;
- dependency/library components do not become feature owners merely because they appear in the manifest;
- existing F-IDs are not implementation tasks and are not renumbered.

## Ownership collision rule

A feature is not declared to have a new owner merely because an Activity, library component, provider, task, repository, or helper appears in its evidence.

A new canonical owner is established only when evidence shows that the component/boundary owns the relevant state, policy, orchestration, result, or execution contract.

If two existing owners appear to cover the same contract, stop at reconciliation; do not create a duplicate owner.

### F04 — Apps inventory / data provider

**Reference evidence**

- `AppListActivity` is the UI entry/consumer and owns presentation/navigation state.
- `tt` is the Apps-list ViewModel/state consumer. Its `k()` delegates loading to a `dv` repository through `dv.i(...)`; its `m()/n()` handle query/filter result state.
- `kz4` is a concrete `dv` repository with static singleton `kz4.g`. Its `a()` is the inventory load boundary.
- `kz4.a()` checks readiness through `dz5.n()/dz5.k()`, initializes related repos, reads the persisted `show_system_apps` preference, then calls `g00.l(showSystemApps)`. It merges the returned local inventory collections and exposes `ji` app models through the generic `dv` result contract.
- `kz4.onAppEvent()` updates/removes inventory entries when package events arrive; new packages are converted with `ji.Companion.fromPackageInfo()` after the same `g00.z(packageInfo, showSystemApps)` inclusion predicate.
- `g00.m(boolean)` independently obtains installed `PackageInfo` values and converts them through `ji.Companion.fromPackageInfo()`; `g00.l(boolean)` is the broader Apps inventory assembly boundary used by `kz4`, including persisted/metadata-backed app information.

**Owner decision**

**CANONICAL OWNER ESTABLISHED: Apps inventory repository = `kz4`; inventory/data assembly dependency = `g00`; app data model = `ji`.**

`AppListActivity` and `tt` remain consumers/state presentation surfaces.

### F05 — Apps batch selection / task-result boundary

**Reference evidence**

- `AppsBatchActivity` is a distinct batch UI surface.
- `r20` is the batch state holder: it stores the selected/filtered app list (`j` / `n`), selected batch action (`i`), UI state (`k`), filter/query state (`p)), and exposes `k(ArrayList, ty7)` to prepare the task input.
- `AppsBatchActivity` receives either `batch_action_item` (`n10`) or `quick_action_item` (`zc6`) and uses the batch state/adapter selection before dispatch.
- `n10` is the batch action descriptor for named batch operations. Its documented predicates identify destructive/selection-sensitive actions such as Uninstall, Delete backups, and Enable/Disable apps.
- `mf` contains the batch dispatch branching: Delete-backups and Enable/Disable are dispatched through dedicated boundaries; Backup/Restore/Sync-related actions expand through `xi0`; label/export actions have their own downstream boundaries.
- `r20.k(ArrayList, ty7)` constructs a `c40` task wrapper through `o20`; `c40` identifies itself as `AppsTask` and receives the selected app/task list plus the `ty7` task mode.
- `c40` is therefore the evidenced execution/task boundary for app batch work; concrete backup/restore work is delegated inside that task rather than owned by `AppsBatchActivity`.

**Owner decision**

**CANONICAL STATE/ORCHESTRATION OWNER: `r20`. CANONICAL APPS TASK EXECUTION OWNER: `c40` (`AppsTask`).**

`AppsBatchActivity` remains consumer/orchestrator UI. The individual action engines remain downstream contracts.

**BaRe cross-check**

Current `com.bare.appslist.ui.listbatch.AppsBatchActivity` has only UI placeholders and stores raw parcelables; no `r20)-equivalent state contract or `AppsTask)-equivalent executor is present.

**Classification:** STATIC EVIDENCE SUFFICIENT / **UNVERIFIED** runtime; execution implementation remains **DEFERRED** to downstream task-engine work.

### F09 — Config model / persistence / validation / task-input chain

**Reference evidence**

- `Config` is the top-level configuration model: id, name, settings list, update date, version; it exposes `getValidSettings()`, `hasValidSettings()`, `isNameValid()`, `isNameTaken()`, `plusSettings()), and `minusSettings()`.
- `ConfigSettings` is the configuration execution-input model. It contains app parts, locations, sync option, backup limits, archive/multiple-backup strategy, restore permissions/SSAID, compression/cache/redo/enabled flags, and `ApplyData`.
- `ConfigSettings.isValid(boolean)` delegates to `ApplyData.isValid(boolean)`; `ApplyData) is valid when its label ids resolve through the label repository, with strict-mode behavior when labels are absent.
- `ConfigsData` is the persisted collection model. It owns the config map and provides `put()`, `remove()`, `getValues()`, `hasConfigs()), and `validate()`; `validate()` removes invalid `Config) entries.
- `br1` is the canonical Config repository boundary. It owns the in-memory `ConfigsData), uses the persistence/cloud key `configs), loads from the configured store, publishes validated state, and exposes duplicate-name checking through `br1.c(Config)`.
- `d76) contains the Reference save path: it rejects invalid `Config), refreshes update date, updates `br1.e), then routes the resulting `ConfigsData) through `ah).
- `ah) validates the incoming `ConfigsData), updates `br1), publishes the validated state, and writes through `br1.c`/the configured persistence boundary.
- Config UI is split across `ConfigListActivity`, `ConfigEditActivity), and `ConfigSettingsActivity`; these consume the model/repository boundaries rather than being the persistence owner.
- `ConfigSettings) exposes normalized execution inputs such as `getAppParts()`, `getLocations()`, and `getSyncOption()`; downstream task/config-run surfaces consume those values.

**Owner decision**

**CANONICAL MODEL = `Config` + `ConfigSettings`; persisted collection = `ConfigsData`; canonical repository/persistence boundary = `br1`; validation/normalization remains in the data-model/repository chain; downstream execution-input projection is separate from the UI.**

Firebase-specific storage/cloud behavior is Reference evidence only. BΛR☰ target provider remains Supabase per project authority; this extraction does not authorize provider implementation.

**BaRe cross-check**

Current `com.bare.appconfigs` contains only the three UI Activities. No `Config)/`ConfigSettings)/`ConfigsData) model or `br1)-equivalent repository is present in the current target source.

**Classification:** STATIC EVIDENCE SUFFICIENT / **UNVERIFIED** runtime; provider/backend execution is **DEFERRED**.
