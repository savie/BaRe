1. Reference evidence
2. canonical owner
3. consumer(s)
4. inputs / triggers
5. outputs / results
6. state
7. dependencies
8. execution boundary
9. P4 contracts consumed
10. implementation target
11. verification surface

Owner rule:
- one canonical owner per contract;
- Activity/Fragment remains a consumer when a domain/service/repository boundary is evidenced;
- provider/backend execution remains behind the appropriate contract when outside the current authorization;
- dependency/library components do not become feature owners merely because they appear in the manifest;
- existing F-IDs are not implementation tasks and are not renumbered.

## Ownership collision rule

A feature is not declared to have a new owner merely because an Activity, library component, provider, task, repository, or helper appears in its evidence.

A new canonical owner is established only when evidence shows that the component/boundary owns the relevant state, policy, orchestration, result, or execution contract.

If two existing owners appear to cover the same contract, stop at reconciliation; do not create a duplicate owner.
