## Raw ZIP audit pass — read-only, no implementation

This pass inspected the decompiled ZIP read-only and followed the existing P6.3 gaps into concrete producers, consumers, identity derivation, and persistence mutators. No ZIP content was modified and no new Supabase implementation was performed.

Newly established facts:

- `users/{uid}/cloud_v1/{sanitized-cloud-dir}` has real read/write/delete/migration behavior, including guarded metadata migration when a cloud account email changes.
- `tags/{cloudTag}/apps/{appId}/{backupId}` is a concrete persisted `CloudMetadata` surface with app/backup identity, per-part artifact metadata, update, partial-delete, and whole-node delete behavior.
- `tags/{cloudTag}/folders/{folderId}` is a concrete persisted `FolderMetadata` surface with explicit validity, write and delete behavior.
- `smsBackupsCount` and `callLogBackupsCount` are read as integer summary metadata; no client-side writer was found in this ZIP pass.
- The local account namespace derivation is directly confirmed as first-half MD5(UID), i.e. a 16-character derived key; this strengthens the identity/backup-namespace contract without proving recovery continuity.
- Contributor Reference storage uses a six-character UID prefix under `contributorDetails`; the target remains full Auth UUID keyed by the P6.2 ownership decision.

Important security finding:

`CloudMetadata` contains password-hash fields for encrypted Data/External-Data/Media parts plus cloud artifact links and encryption metadata. `prepareForFirebaseUpload()` strips several local-only/sensitive runtime fields before persistence, but the inspected code does not establish that these password-hash fields are secret-free. P6.3 therefore must treat them as **sensitive persisted backup metadata**, not ordinary profile data, and must complete target protection/RLS/data-classification analysis before any Supabase modeling.

## Raw ZIP audit pass 2 — cloud namespace, migration, and upload sanitization

- cloud_v1 is user-scoped and keyed by a sanitized currentCloudDir; the sanitizer removes slash, dot, hash, dollar, bracket and related Firebase-invalid characters before producing the child key.
- account-email migration reads source/destination cloud metadata, applies guards, writes the destination, then deletes the old source metadata; exact target transaction/atomicity remains UNKNOWN.
- CloudMetadata.prepareForFirebaseUpload() clears permission IDs/states, notification/accessibility components, SSAID, and legacy per-part SB-version fields, while retaining data/ext-data/media password hashes.
- This means CloudMetadata is sensitive persisted backup metadata, not harmless display metadata.

## Raw ZIP audit pass 3 — metadata versus artifact boundary

- CloudMetadata is a persisted descriptor/state object; restore resolves external artifacts from metadata + selected parts, then downloads or reuses them through the cloud-provider boundary.
- Upload/update is part-oriented: rebuilt parts update their corresponding metadata descriptors while unchanged parts may be retained/reused.
- Deletion is part-aware: individual part metadata can be cleared without immediately deleting the whole backup node; the whole metadata node is removed only when no cloud files remain.
- Therefore target architecture must keep persisted backup metadata separate from external cloud artifact storage/access. The Reference evidence does not justify assuming Supabase Storage is the artifact store.

## Raw ZIP audit pass 4 — CloudMetadata field lifecycle

- Aggregate identity/state includes packageName, name, versionName/versionCode, dateBackup/dateBackupUpdated, and backup identity via AppCloudBackup backupId.
- Each artifact group has link, size, mirrored size where applicable, backup date, compatibility requirements, and for encrypted Data/External-Data/Media: encryption state, method, and password hash.
- updateDataDetails/updateExtDataDetails/updateMediaDetails replace the complete descriptor group as a unit; APK/splits/shared-libs/expansion/special-data have corresponding update groups.
- prepareForFirebaseUpload clears local-only fields and legacy per-part compatibility fields but retains the three password hashes; minSBVersionCodeRequired remains the aggregate compatibility requirement.
- protection/note have explicit mutation semantics; keyVersion is persisted but its security/rotation meaning is still UNKNOWN.
- No target table was created from this model. Remaining design questions are field sensitivity/authorization, normalization, artifact-key semantics, and cross-part atomicity.

## Raw ZIP audit pass 5 — FolderMetadata field lifecycle and reconciliation

This pass inspected the decompiled ZIP read-only. No ZIP content was modified and no Supabase schema was created from this evidence.

### FolderMetadata shape

- FolderItem: id, displayName, sourceFolder, setupCreationTime.
- BaseBackup: backupLink, backupSize, originalSize, manifestLink, manifestSize, timestamp; isBaseBackup is transient.
- IncrementalBackup map: keyed by timestamp; each entry has backupLink, backupSize, originalSize, manifestLink, manifestSize, timestamp; isBaseBackup is transient.
- latest backup date and total size are derived from child metadata rather than independently stored values.

### Local producer / reconciliation

kj3 discovers and validates local base/incremental files, loads the metadata file, and FolderMetadata.refreshLocalMetadataFile() rebuilds metadata from the actual backup and manifest files. The local metadata file is rewritten only when the rebuilt snapshot differs.

### Cloud producer / write

FolderMetadata.writeToFirebaseNode() requires a valid FolderItem, valid cloud links, a valid base backup, and valid incremental backups before writing the metadata node at folders/{folderId}. FolderItem.writeToFirebaseNode() separately writes folder identity/configuration under folders/{folderId}/folderItem.

### Upload reconciliation

The upload task compares local and cloud base/incremental sizes. Equivalent snapshots are skipped. Replacing a different cloud snapshot first deletes the existing cloud backup, then uploads the local artifacts. Uploaded results rebuild the corresponding metadata links; duplicate incremental timestamps are detected. If the resulting metadata has no backups or invalid links, newly uploaded artifacts are cleaned up.

### Cloud delete

al3 removes the folder metadata node first, then collects and deletes the base/manifest and every incremental/manifest artifact through the external cloud provider. This confirms metadata and artifact storage are separate concerns.

### B04 blueprint

Evidence is sufficient to draft, but not yet execute, a normalized target:

Auth user → folder_backups (folder identity/config + ownership) → folder_base_backups (0..1) + folder_incremental_backups (0..N).

Artifact references remain behind CloudProviderRepository. Derived latest-date/total-size values should be computed unless a later consumer proves denormalized storage is required.

Before schema execution, lock exact owner/RLS predicates, sourceFolder local-vs-backend classification, artifact-link sensitivity, incremental identity/collision semantics, metadata/artifact atomicity, and whether Supabase Storage is used at all.


## Security / ownership audit pass — B02/B04

### B02 — cloud account identity is not BaRe identity

`re3.j()` uses the authenticated Firebase UID for the `users/{uid}` owner boundary. Separately, `qb1.i()` builds the current cloud account identity from the selected provider credential's display account ID when available, otherwise from the stored/current cloud email; `re3.g()` sanitizes that value for the `cloud_v1` child key.

Therefore the Reference has two identity dimensions:

- BaRe/backend user identity = authenticated UID;
- external cloud account identity = provider/account-derived value.

Target consequence: the sanitized `cloud_v1` child key is a Reference namespace key, not a candidate Auth primary key. A BaRe target should keep Auth UUID as ownership and retain only the minimum provider/account reference needed by the cloud boundary.

### B04 — sourceFolder is a sensitive local-path field

`FolderItem.sourceFolder` is a local filesystem path. `FolderMetadata.writeToFirebaseNode()` serializes the complete FolderMetadata object, which contains FolderItem, so the Reference cloud payload includes sourceFolder. This proves Reference persistence, but it does not prove that a remote backend needs the exact local path for BaRe functionality.

Target consequence: classify sourceFolder as sensitive/local-context data. Before schema execution, decide whether BaRe needs it at all; if it does, store only the minimum necessary representation under user ownership. Do not expose it through broad/public reads.

### B04 — artifact links are external-provider references

Folder download constructs provider-download work directly from BaseBackup/IncrementalBackup backupLink and manifestLink. Cloud delete passes those links to the external cloud client. The evidence therefore supports treating artifact links as provider-owned references, not as proof of Supabase Storage objects.

### Atomicity boundary

Reference reconciliation is multi-step: metadata read/compare → optional external artifact delete → artifact upload/download/delete → metadata write/delete. The decompiled client does not establish a single atomic transaction spanning Firebase metadata and the external provider. Target should therefore not claim atomicity unless BaRe explicitly implements compensating/reconciliation semantics.


## Security / ownership audit pass — B03 password-derived metadata

`CloudMetadata.dataPasswordHash`, `extDataPasswordHash`, and `mediaPasswordHash` are not dead fields: the backup decision path reads them from cloud metadata and passes them into comparison/decision logic. The decompiled source does not establish how those hashes are constructed, whether they are salted/one-way in a target-safe sense, or whether they can be treated as non-sensitive.

Target consequence: classify these fields as **secret-like sensitive metadata** until a complete cryptographic contract is recovered. Do not place them in a broad user-profile table, do not expose them through generic backend reads, and do not assume Reference persistence is a security recommendation.

`CloudMetadata` artifact links are also consumed as inputs to cloud download/delete operations. Their presence proves a provider-reference contract, not a requirement for public URLs or Supabase Storage. Target access should remain behind the provider boundary and user ownership checks.


## B02 migration atomicity audit — refined result

Raw ZIP `fu3.t()` gives a stronger recovery contract than a simple read/write/delete sequence:

- source and destination cloud-account metadata are inspected before migration;
- destination/source guards prevent migration when the expected state is not present;
- destination metadata is written first;
- old source metadata is deleted afterward;
- if the source changes during cleanup, the flow can restore/rollback the destination when the destination has not independently changed;
- the flow may retry the migration after a source-change race;
- if the destination also changed, rollback is skipped rather than blindly overwriting it.

This is **application-level compare/guard/compensate behavior**, not proof of a single atomic backend transaction.

Target consequence: B02 should model migration as an explicit reconciliation workflow. Do not require a database transaction spanning the old and new external-cloud namespace, because the Reference itself crosses provider metadata and external-cloud identity boundaries. BaRe should instead define idempotent/guarded migration plus compensation behavior if migration remains a supported lifecycle.
