## Status vocabulary

- **AUDIT REQUIRED** — Reference behavior is known to exist, but the field-complete target contract is not yet safe to implement.
- **DEFINED** — Target owner and contract are sufficiently bounded for implementation.
- **IMPLEMENTED** — Target code/schema has been changed.
- **TESTED** — Target behavior has been exercised by an appropriate test.
- **VERIFIED** — Evidence proves the required behavior at the current verification boundary.
- **UNKNOWN** — Evidence is insufficient; do not assume.
- **DEFERRED** — Explicitly held because an upstream dependency or contract is not yet resolved.
- **DO NOT MODEL** — Reference evidence exists but the target architecture intentionally does not reproduce that mechanism.
- **NOT REQUIRED** — Contract/audit establishes that no target implementation is needed.

IMPLEMENTED ≠ VERIFIED.

- crowdin_id text
- paypal_id text

Constraint:

type IS NULL OR type IN (TRANSLATOR, COMMUNITY_HELPER)

Direct inspection on the target confirmed both tables, all approved columns, both PK/FK relationships, the contributor type constraint, and zero application rows. Security advisor still reports RLS disabled on both public tables; this remains an explicit downstream security blocker and is not marked verified.

## What P6.3 does NOT mean

P6.3 may investigate and implement unresolved contract items when their evidence supports doing so. It must **not** mechanically turn every Reference Firebase path into a Supabase table.

The following are not yet claimed as complete merely because the initial tables exist:

- Supabase Auth/session lifecycle;
- app ↔ Supabase adapter implementation;
- credential persistence/protection mechanism;
- external cloud credential storage;
- final RLS policies and least-privilege authorization;
- Storage;
- Edge Functions;
- field-complete cloud_v1 / cloud-tag model;
- standalone backend verification;
- APK/runtime verification.

These are represented by the register rows and later P6 lifecycle boundaries where appropriate.

## Raw ZIP audit pass — read-only, no implementation

This pass inspected the decompiled ZIP read-only and followed the existing P6.3 gaps into concrete producers, consumers, identity derivation, and persistence mutators. No ZIP content was modified and no new Supabase implementation was performed.

Newly established facts:

- `users/{uid}/cloud_v1/{sanitized-cloud-dir}` has real read/write/delete/migration behavior, including guarded metadata migration when a cloud account email changes.
- `tags/{cloudTag}/apps/{appId}/{backupId}` is a concrete persisted `CloudMetadata` surface with app/backup identity, per-part artifact metadata, update, partial-delete, and whole-node delete behavior.
- `tags/{cloudTag}/folders/{folderId}` is a concrete persisted `FolderMetadata` surface with explicit validity, write and delete behavior.
- `smsBackupsCount` and `callLogBackupsCount` are read as integer summary metadata; no client-side writer was found in this ZIP pass.
- The local account namespace derivation is directly confirmed as first-half MD5(UID), i.e. a 16-character derived key; this strengthens the identity/backup-namespace contract without proving recovery continuity.
- Contributor Reference storage uses a six-character UID prefix under `contributorDetails`; the target remains full Auth UUID keyed by the P6.2 ownership decision.

Important security finding:

`CloudMetadata` contains password-hash fields for encrypted Data/External-Data/Media parts plus cloud artifact links and encryption metadata. Pass 2 directly inspected `prepareForFirebaseUpload()`: it clears `permissionIdsCsv`, `permissionStatesCsv`, `ntfAccessComponent`, `accessibilityComponent`, `ssaid`, and legacy per-part SB-version fields, and sets `minSBVersionCodeRequired`; it **does not clear** `dataPasswordHash`, `extDataPasswordHash`, or `mediaPasswordHash`. P6.3 therefore treats those hashes and related cloud artifact metadata as **sensitive persisted backup metadata** until the target security contract is explicitly resolved. This is Reference behavior evidence, not a recommendation to copy the same storage shape into Supabase.

## Status vocabulary

- **AUDIT REQUIRED** — Reference behavior is known to exist, but the field-complete target contract is not yet safe to implement.
- **DEFINED** — Target owner and contract are sufficiently bounded for implementation.
- **IMPLEMENTED** — Target code/schema has been changed.
- **TESTED** — Target behavior has been exercised by an appropriate test.
- **VERIFIED** — Evidence proves the required behavior at the current verification boundary.
- **UNKNOWN** — Evidence is insufficient; do not assume.
- **DEFERRED** — Explicitly held because an upstream dependency or contract is not yet resolved.
- **DO NOT MODEL** — Reference evidence exists but the target architecture intentionally does not reproduce that mechanism.
- **NOT REQUIRED** — Contract/audit establishes that no target implementation is needed.

IMPLEMENTED ≠ VERIFIED.

## P6.3 working rule

When a new Reference finding appears:

1. **Audit the Reference evidence.**
2. **Add or update one canonical register row.**
3. **Define the owner/boundary.**
4. **Choose the target decision.**
5. **Implement in Supabase, app, both, provider boundary, or nowhere as justified.**
6. **Verify at the strongest currently authorized boundary.**
7. **Re-audit the row and update its status/evidence.**

Do not create a new phase or a new audit document solely because a new backend finding appears.
