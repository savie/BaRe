## P6.1 contract rule

The canonical ownership chain is:

`UI / feature consumer → provider-neutral domain/repository boundary → Supabase adapter → Supabase service/backend`

Provider SDK types must not cross the provider-neutral consumer boundary.

The current BaRe backend interfaces satisfy this static boundary.

## Identity boundary

Canonical flow:

`Account lifecycle → provider-neutral BackendIdentity → Supabase Auth identity`

The current `BackendIdentity` is provider-neutral and contains no Supabase/Firebase
SDK type.

External backup-cloud identity remains separate:

`BaRe backend identity ≠ external cloud-provider identity`

`CloudProviderRepository` owns external backup-cloud access.

P6.1 therefore closes the ownership decision that the Supabase adapter must
implement BaRe backend identity without becoming the owner of external cloud
provider credentials or authorization.

## User-info boundary

Current target contract:

`UserInfoRepository.load(uid) / save(UserInfo)`

Reference evidence establishes `users/{uid}/userInfo` as a Reference backend
relationship, but the path is not a target schema definition.

P6.1 therefore records:

- `UserInfoRepository` owns the provider-neutral persistence boundary.
- `UserInfo` is the canonical target-side model currently exposed to consumers.
- Exact Supabase table/column/relationship design remains P6.2.
- Anonymous-user behavior must not be invented beyond the audited Reference
  contract.
- No Firebase SDK type is allowed to cross this boundary.

## BaRe backend boundary

Current interface:

`BaReBackendRepository`

Static responsibilities already represented by the interface:

- current backend-neutral identity;
- user-info load;
- user-info save;
- registered-contributor state;
- sign-out lifecycle boundary;
- current cloud-directory metadata.

P6.1 does not claim that these operations are already implemented against

## External cloud boundary

Current interface:

`CloudProviderRepository`

Static responsibilities represented by the interface:

- external cloud access state;
- authorization recovery;
- external provider/cloud-folder metadata.

This boundary is not merged into `BaReBackendRepository`.

Supabase owns BaRe backend concerns. External cloud providers retain their own
identity and authorization boundary.

## Data classification

P6.1 uses the project-approved classification vocabulary:

- `LOCAL_ONLY`
- `LOCAL_PERSISTED`
- `CLOUD_PERSISTED`
- `BACKEND_DERIVED`
- `PROVIDER_DERIVED`
- `RUNTIME_ONLY`
- `SECRET/CREDENTIAL`
- `MIXED_LOCAL_CLOUD`

### Current classification decisions

| Data / state | Classification | Ownership decision |
|---|---|---|
| `BackendIdentity` fields | `BACKEND_DERIVED` | Derived from BaRe backend identity/Auth; not an external provider credential store |
| `UserInfo` persisted representation | `CLOUD_PERSISTED` candidate | Exact fields/relationships remain P6.2 target-model work |
| Account lifecycle transient state | `RUNTIME_ONLY` | Remains in lifecycle/runtime boundary unless separately evidenced as persisted |
| External cloud connection state | `PROVIDER_DERIVED` | Owned by external `CloudProviderRepository` |
| External provider credentials | `EXTERNAL_PROVIDER_ONLY` / `SECRET/CREDENTIAL` | Must not be copied into ordinary BaRe backend tables |
| Reference Firebase paths | `REFERENCE_EVIDENCE` | Audit evidence only; never target persistence by path name |
| Backend-derived status | `BACKEND_DERIVED` | Must be defined by approved contract before persistence |
| Local/backend reconciled state | `MIXED_LOCAL_CLOUD` | Requires explicit P6.2 synchronization ownership |

A classification of `CLOUD_PERSISTED` is not permission to create a table yet.
The actual target model is P6.2.

## Credential boundary

Reference credential-shaped contracts are evidence only.

P6.1 adopts the approved credential categories:

- `NEVER_BACKEND`
- `LOCAL_SECURE_STORAGE`
- `SUPABASE_AUTH`
- `SUPABASE_DATABASE`
- `EXTERNAL_PROVIDER_ONLY`
- `TRANSIENT_MEMORY`

Default rule:

Provider secrets, private keys, encryption keys, passwords, and access/refresh
tokens are not ordinary application-table data without explicit evidence and
authorization.

Service-role credentials are never client-embedded.

P6.1 therefore closes the **classification boundary**, not the actual secret
storage implementation.

## Reference backend quarantine

Reference evidence includes paths such as:

- `appData`
- `users/{uid}`
- `users/{uid}/userInfo`
- `users/{uid}/cloud_v1`
- `tags/{cloudTag}/apps`
- `tags/{cloudTag}/folders`
- `tags/{cloudTag}/smsBackupsCount`
- `tags/{cloudTag}/callLogBackupsCount`
- `purchase_verifications/{uid}/<obfuscated key>`

These remain evidence for behavior, ownership, payloads, and relationships.

They are **not** a Supabase schema proposal.

Target translation remains:

`Reference evidence → BaRe contract → Supabase target model`

Never:

`Firebase path → automatic Supabase table`

## Verification surface

P6.1 defines what must later be verified in P6.8:

### Identity

- Auth identity maps to provider-neutral `BackendIdentity`.
- Anonymous/registered state follows the approved account lifecycle contract.
- External cloud-provider identity remains separate.

### Persistence

- User-info load/save behavior matches the approved contract.
- Ownership and relationships are enforced by the target backend.
- Backend-derived values are not silently treated as client-owned state.

### Authorization

- Backend resources have explicit ownership.
- Read/write/update/delete behavior is authorized.
- Cross-user isolation is testable.
- RLS is verified where the target exposes persisted data.

### Credentials

- Secret classification is preserved.
- No credential leakage into ordinary application tables.
- No service-role credential in client implementation.

### Boundary

- No Supabase SDK types leak into provider-neutral consumers.
- No external cloud-provider credential model is collapsed into BaRe backend
  identity.
- Reference evidence remains isolated from target schema.
