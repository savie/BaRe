## 1. Target-model principles

### 1.1 Supabase Auth owns backend identity

Canonical identity flow:

`Account lifecycle → BackendIdentity → Supabase Auth identity`

The target does not create an application-table replacement for `auth.users`.

Supabase-managed `auth.users.id` is the stable foreign-key anchor for
application-owned user data.

### 1.2 Application data is separate from Auth

Reference `users/{uid}/userInfo` establishes a user-owned profile/persistence
relationship, not a literal SQL table name.

Target representation:

`auth.users (1) → user_profiles (0..1)`

### 1.3 Anonymous state is Auth-derived

Reference `UserInfo` contains `anonymous`, but the target does not need to
persist a second source of truth for this value.

Supabase Auth already distinguishes anonymous users and exposes that state through
the Auth user/session model.

Therefore:

- `BackendIdentity.anonymous` = derived from Supabase Auth;
- `user_profiles` does **not** own an independent `anonymous` flag;
- the adapter must not allow profile data to override Auth identity state.

This avoids identity divergence.

### 1.4 External cloud identity stays separate

The Reference `cloud_v1` and `FireHelper.currentCloudDir` evidence does not
make an external backup-cloud account a BaRe Auth identity.

Canonical boundary remains:

`BaRe backend identity ≠ external cloud-provider identity`

`CloudProviderRepository` remains the owner of external provider access and
provider credentials.

## 2. Supabase target resources

### 2.1 Supabase Auth — managed resource

**Resource:** `auth.users`

**Owner:** Supabase Auth

**Target responsibility:**

- user identity;
- authentication identity;
- anonymous/permanent distinction;

**Application access rule:**

The app consumes provider-neutral `BackendIdentity`; it must not expose

No custom `users` table is proposed.

### 2.2 `public.user_profiles` — approved target model

This is the target-side persistence model for the Reference `userInfo`
contract.

| Column | Type | Required | Source/meaning | Owner |
|---|---|---:|---|---|
| `id` | uuid | yes | Supabase Auth user ID / Reference uid | Auth identity boundary |
| `display_name` | text | no | Reference `displayName` | UserInfoRepository |
| `email` | text | no | Reference `email` snapshot | UserInfoRepository |
| `photo_url` | text | no | Reference `photoUrl` | UserInfoRepository |
| `latest_app_version` | integer | yes | Reference `latestAppVersion` | UserInfoRepository |
| `current_app_version` | integer | yes | Reference `currentAppVersion` | UserInfoRepository |

Constraints:

- primary key: `id`;
- foreign key: `id → auth.users.id`;

The exact Reference version initialization/update behavior remains an adapter
responsibility; the schema does not hard-code version 620 as a database

### 2.3 `public.contributor_registrations` — approved target model

`load(uidPrefix)` / `isRegistered(uidPrefix)`.

The target must not use the six-character UID prefix as the database primary

Target representation:

`auth.users (1) → contributor_registrations (0..1)`

| Column | Type | Required | Source/meaning |
|---|---|---:|---|
| `user_id` | uuid | yes | Auth user identity |
| `status` | text | no | Reference registration status |
| `type` | text | no | `TRANSLATOR` / `COMMUNITY_HELPER` |
| `name` | text | no | Contributor name |
| `locales` | text | no | Translator/community locale data |
| `telegram_id` | text | no | Reference Telegram identifier |

- primary key: `user_id`;
- foreign key: `user_id → auth.users.id`;

- translator validity remains domain logic, not a database-only CHECK;
- no provider credential/token is implied by these identifier fields.

The adapter may derive the Reference UID prefix from the authenticated UID when
calling a compatibility path, but the target database identity remains the

### 3.2 `appData` / `activeSkus`

**Target decision: DO NOT MODEL for Premium access.**

No fake SKU/catalog backend is introduced merely to preserve Reference billing.

### 3.3 `FireHelper.currentCloudDir`

This is a current external-cloud directory/metadata value.

**Target decision: NOT a Supabase Auth identity and not a standalone
application-user table.**

Ownership remains with the external cloud/provider boundary.

### 3.4 External cloud credentials

Reference credential persistence is evidence only.

**Target decision: NOT ordinary Supabase application-table data.**

Provider passwords, private keys, access/refresh tokens, and encryption
material remain under the credential boundary established in P6.1.

#### 3.4.1 External cloud integration mechanism

External cloud integration remains part of the Reference-derived feature surface.
The target architecture must preserve a provider-neutral cloud boundary rather
than hard-coding provider credentials into the Android client or ordinary user
profile rows.

Canonical separation:

`BaRe backend identity ≠ external cloud-provider identity`

`CloudProviderRepository → provider-specific authorization/access mechanism`

Examples include Google Drive, OneDrive, Dropbox, or another supported provider.
The frontend may initiate the provider's authorization flow, but user passwords,
access tokens, refresh tokens, private keys, or equivalent secrets must not be
hard-coded in source code or stored in `public.user_profiles` merely to make
cloud integration work.

Reference evidence that a credential or provider-access value is persisted does
not, by itself, define the target secure-storage mechanism. P6 therefore keeps
credential handling **IN SCOPE** while requiring the concrete persistence and
protection mechanism to be explicitly defined before implementation.

This is an implementation-boundary decision, not a removal of external cloud
support from BΛR☰.

## 6. Ownership and authorization model

### `user_profiles`

Owner: authenticated user represented by `auth.uid()`.

Required target authorization:

- authenticated user can read own row;
- authenticated user can create own row;
- authenticated user can update own row;
- authenticated user can delete own row only if later contract requires deletion;
- no user can access another user's profile row through the Data API;
- anonymous users are handled according to the account lifecycle contract and
  Auth state, not by a spoofable profile column.

### `contributor_registrations`

Owner: authenticated user represented by `auth.uid()`.

Required target authorization:

- authenticated user can read own registration;
- authenticated user can write/update own registration where the Reference
  registration flow authorizes mutation;
- no user can read or modify another user's registration;
- contributor eligibility is not encoded in user-editable Auth metadata.

The final RLS SQL belongs to P6.5 implementation/security work, not P6.2.

## 9. Supabase-specific target constraints

The current Supabase platform requires explicit attention to both Postgres
grants and RLS for exposed application tables. New public tables are no longer
automatically exposed to the Data API under the current rollout, so P6.3/P6.5
must explicitly configure grants/exposure as part of implementation and
security verification.

The target must use:

- Auth-owned `auth.users` identity;
- application tables with explicit ownership predicates;
- RLS on exposed application tables;
- no `user_metadata` authorization decision;
- no service-role/secret key in the Android client.

These are implementation/security constraints, not reasons to alter the
provider-neutral contract.

## 11. P6.2 exit decision
