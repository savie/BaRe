# BΛR☰ — Namespace Migration Map

**Status:** Planning artifact only. No application source, APK, reference snapshot, workflow, or native library was modified by this map.

**Evidence basis:** `docs/namespace-audit/BaRe-namespace-inventory.md` and `docs/namespace-audit/BaRe-namespace-hits.csv`, generated from the SwiftBackup 5.1.0 (620) Apktool/JADX decompilation snapshot. Categories below combine observed inventory findings with engineering risk assessment; they are not proof that every individual occurrence has been semantically inspected.

## Classification legend

- **SAFE (low risk, scoped):** Can normally be changed when the exact resource/field is confirmed to be user-facing and all references are updated. Still require diff and build checks.
- **RUNTIME CHECK (controlled migration):** Can affect linking, reflection, persisted data, external integrations, Android component resolution, or native calls. Map callers and consumers first, then test.
- **KEEP (do not mass-replace):** Third-party/dependency contracts, generated IDs, opaque binary content, or identifiers whose ownership/semantics are not established. Revisit only with evidence and an explicit migration plan.

## Suggested migration sequence

### Phase 0 — Freeze and establish baseline
1. Keep `reference/apktool` and `reference/jadx` unchanged.
2. Work only in `bare-implementation/`; do not edit `BareApp.kt`.
3. Record the current known-good APK hash, signing certificate fingerprint, package ID, version, and CI run.
4. Preserve the current working build so every phase can be compared against a baseline.

### Phase 1 — Branding values only
1. Change the launcher label and confirmed user-facing copy; keep resource keys and class names intact.
2. Review all locale-specific values and logger/share/notification text.
3. Build, install, launch, and test sign-in plus primary screens.

**Gate:** no resource-ID churn; app launches; sign-in still succeeds.

### Phase 2 — App package and Android component contract
1. Enumerate every manifest component, provider authority, permission, intent action, deep link, reflection string, and descriptor that belongs to the app.
2. Prepare an explicit old-to-new mapping for app-owned identifiers only.
3. Apply the package migration consistently in the implementation copy.
4. Keep third-party namespaces and native contracts untouched unless separately approved.

**Gate:** manifest assertions pass; clean install and upgrade both work; no class-not-found, provider-authority, or verifier errors.

### Phase 3 — Native/JNI and archive libraries
1. Build a per-ABI table of library names, exported JNI symbols, matching Smali declarations, and known source availability.
2. Verify `libnative-lib.so`'s three functions separately from `libsba_archive.so` and all other native libraries.
3. Do not rename `com.swiftapps.sba` or `SwiftTar` without source/ownership confirmation and a coordinated ABI migration.

**Gate:** symbol checks pass for all included ABIs; native calls, archive backup/restore, and local-network permission checks pass on device.

### Phase 4 — Backend and persisted-data compatibility
1. Validate Firebase/OAuth configuration against the final package ID and signing certificate.
2. Test account lifecycle, token refresh, cloud connectivity, and any entitlement checks.
3. Test old backup files, archive metadata, preferences, scheduled jobs, and restore paths.

**Gate:** login works on the signed artifact; backup/restore round-trip succeeds; old user data remains readable.

### Phase 5 — Remove workflow-side source mutation
Once configuration and source edits are committed to `bare-implementation/`, simplify CI to checkout, deterministic validation, native compilation where intentionally source-owned, Apktool build, signing, and artifact publication. It should not silently pull strings or Firebase config from `rewrite` or rewrite application source during CI.

**Gate:** two builds from the same commit produce equivalent application contents (allowing for expected signing/build metadata); workflow logs identify every generated/modified artifact.

## Required automation checks before any migration commit

- [ ] Assert manifest package and app label.
- [ ] Check all declared component classes exist in the expected Smali paths.
- [ ] Check provider authorities and permission names are consistent and unique.
- [ ] Compare resource ID mappings before/after; fail on unexpected changes.
- [ ] Scan for residual app-owned old package references and review every remaining hit by category (do not require zero occurrences globally).
- [ ] Verify JNI exports and matching native declarations for each ABI.
- [ ] Build and sign using the stable signing key; never commit the keystore or passwords.
- [ ] Install/upgrade test, launch, login, backup, restore, and archive round-trip.
- [ ] Keep a rollback point for each phase.

## Important interpretation notes

- Inventory counts are raw occurrences; repeated descriptors and generated resources inflate totals.
- This map classifies patterns and areas, not every row in the CSV. Individual hits must be reviewed in context before changing them.
- A successful build is not runtime proof. Each phase must pass its gate before proceeding.
- No implementation changes are authorized or performed by this planning document.
